# 第 11 章：稳定服务

> **状态：PASS**（实测，两套环境）。证据：[`ch11-guardrails.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch11-guardrails.json)（Apple M4 Pro / 135M）、[`ch11-guardrails_large.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch11-guardrails_large.json)（RTX 4080 SUPER / 1.7B）。

第 04 章的服务能回答请求，但经不起真实流量：来 24 个请求它就排 24 个队，最慢的要等几秒到十几秒；客户端走了它还在算；进程挂了没人拉起来。这一章给它加上最小的一套“护栏”，并逐条验证。

```bash
# 一条命令启动（守护进程 + 服务）
PORT=8000 MAX_INFLIGHT=4 QUEUE_TIMEOUT=1 MAX_SECONDS=2 \
  .venv/bin/python -m experiments.ch11.supervisor -- .venv/bin/python -m experiments.ch11.server

# 端到端验证（约 1.5 分钟）
.venv/bin/python -m experiments.ch11.verify
MODEL_SIZE=large DTYPE=bfloat16 python -m experiments.ch11.verify   # GPU 上跑 1.7B
```

代码三份：`experiments/ch11/server.py`（服务）、`supervisor.py`（进程守护）、`verify.py`（验证）。

## 七项护栏

| 护栏 | 做法 | 解决什么 |
|---|---|---|
| 存活 / 就绪探针 | `/healthz` 只说明进程活着；`/readyz` 要模型加载并预热完才返回 200，否则 503 | 负载均衡不会把流量转给还在加载的实例 |
| 准入控制 | 在途请求（运行 + 排队）超过 `MAX_INFLIGHT` 直接回 **429**，带 `Retry-After` | 过载时快速失败，不让队列无限变长 |
| 排队超时 | 等引擎超过 `QUEUE_TIMEOUT` 回 **503** | 给等待设上限 |
| 生成时限 | 单个请求占用引擎超过 `MAX_SECONDS` 就截断，`finish_reason: "timeout"` | 一个超长请求不能独占引擎 |
| 断开回收 | 流式请求客户端中途断开，立即释放名额和引擎锁 | 没人看的生成不继续占算力 |
| 结构化日志与指标 | 每个请求一行 JSON（含 `request_id`、状态、token 数、首 token / 总耗时）；`/metrics` 给计数 | 出问题能追到具体请求 |
| 崩溃恢复与优雅关闭 | 守护进程在子进程退出后重启；SIGTERM 时先把在途请求送完 | 挂了自动恢复；发布时不打断用户 |

一个实现上的细节：排队超时要返回真正的 503 状态码，就必须在发出响应头**之前**拿到引擎。所以流式请求先取出第一个 token（也就是做完 Prefill），再开始发送 SSE——首 token 的时间没有变化，只是状态码的时机对了。

## 实测结果

护栏参数：`MAX_INFLIGHT=4`、`QUEUE_TIMEOUT=1 s`、`MAX_SECONDS=2 s`。两套环境的结论一致：

| 场景 | 135M / MPS | 1.7B / RTX 4080 SUPER |
|---|---|---|
| 进程启动后多久 `/healthz` 通 / `/readyz` 通 | 2.72 s / 5.19 s | 5.51 s / 7.66 s |
| 加载期间来聊天请求 | 503 | 503 |
| 24 个并发请求：200 / 429 / 503 | 3 / 20 / 1 | 2 / 20 / 2 |
| 429 的响应时间（中位数） | 0.01 s | 0.02 s |
| 护栏下最慢的响应 | 1.02 s | 1.47 s |
| **同样 24 个请求打第 04 章的服务，最慢的响应** | 8.07 s | **18.29 s** |
| 排队超时的 503 耗时 | 1.01 s | 1.01 s |
| 要求 512 token 的请求被截断 | 2.01 s，产出 192 个 token | 2.02 s，产出 95 个 token |
| 客户端断开后名额回收 | 0.06 s | 0.04 s |
| `kill -9` 后重新就绪 | 6.4 s | 8.9 s |
| SIGTERM 时正在流式的请求 | 48 个 chunk 全部收到，进程以 0 退出 | 同左 |

读这张表要注意：

- **护栏没有让服务变快**，只是把“最坏情况”从 8—18 秒压到 1—1.5 秒：能服务的服务，不能服务的立刻告诉客户端。被拒绝的请求需要客户端重试或降级，这是产品层面的决定。
- 24 个请求里只有 2—3 个成功——这是 `MAX_INFLIGHT=4` 加 1 秒排队上限的直接结果，参数该怎么设取决于你的流量和延迟目标，不是这里的数字能替你决定的。
- 恢复时间主要是重新加载模型。模型越大，这个数越大；生产上要靠多副本，让一个副本重启时另一个接流量，本书没有验证多副本。

## 验证过程中真正踩到的五个坑

这些都是跑实验时遇到的，不是事先设计的：

1. **断开后名额不回收。** 第一版用同步生成器写 SSE，客户端断开后 10 秒内在途计数都没有回到 0，随后的请求拿到 503。改成异步生成器、每个 token 检查 `request.is_disconnected()`，并在后台线程里关闭引擎生成器后，回收只要 0.06 s。
2. **并发请求在 Mac 上让进程崩溃。** 对第 04 章的服务打 24 个并发请求时，Metal 报 `failed assertion ... setCurrentCommandEncoder` 后进程退出（只遇到过这一次）。我们的判断是：把 token ids 搬到设备上这一步发生在引擎锁外，多线程同时碰设备。现在 `encode_chat` 只在 CPU 上分词，搬到设备放进引擎锁内，之后同样的突发重复跑了几次都没有再崩——这个因果没有做单独的对照实验。
3. **SIGTERM 的退出码是 241。** uvicorn 优雅退出后会把收到的信号重新抛出，进程实际是被 SIGTERM 终止的（退出码 −15，shell 里显示 241）。守护进程要把“自己要求停止时的 −15”视为正常。
4. **429 在 GPU 机器上一度“慢了 1 秒”——其实是测量误差。** 服务端日志显示处理耗时 0 ms，但客户端量到 1.05—1.2 s。我们的判断是 `httpx.post` 每次调用都新建客户端并重建 SSL 上下文，24 个线程在这台机器上互相排队。改成共用一个 `httpx.Client` 后，429 变成 0.01—0.05 s。**压测客户端本身也会成为瓶颈**，第 09 章的压测工具用的是共享连接池，不受影响。
5. **日志行互相穿插。** 第一次在“洁净室”里从头复现时，验证脚本解析日志失败：两条 JSON 被挤在同一行。`print()` 把正文和换行拆成两次写入，多线程并发时会交错。现在每条日志用一次 `write` 写完整行并加锁，验证里也新增了“每一行都是一个合法 JSON”的断言。这个问题在本机连续跑了几次都没暴露，是干净环境那次才撞上的——**并发缺陷靠运气是测不出来的**，所以要有断言。

## 边界

- 只做了单机单进程。多副本、网关限流、鉴权、TLS 都不在验证范围里。
- 非流式请求在客户端断开后会继续算到结束（受 `MAX_SECONDS` 约束），没有做取消。
- `kill -9` 恢复时丢失的是**在途请求**，客户端要自己重试。
- 本机没有 Docker，所以本书没有提供容器镜像——没有验证过的 Dockerfile 不放进来。
