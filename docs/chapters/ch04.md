# 第 04 章：HTTP 服务与流式输出

> **状态：PASS**（实测）。证据：[`ch04-http_stream.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch04-http_stream.json)。

## 这一章要做成什么

一个最小服务：`GET /health`、`POST /v1/chat/completions`，请求/响应形状兼容 OpenAI，支持 `stream: true`。

```bash
.venv/bin/python -m experiments.ch04.server
```

另开一个终端用 curl：

```bash
curl -s localhost:8000/v1/chat/completions -H 'content-type: application/json' \
  -d '{"messages":[{"role":"user","content":"Hi"}],"max_tokens":32}'
```

流式调用只需加 `"stream": true`，并用 `curl -N` 关闭缓冲：

```bash
curl -N localhost:8000/v1/chat/completions -H 'content-type: application/json' \
  -d '{"messages":[{"role":"user","content":"Tell me a story"}],"stream":true}'
```

Python 客户端见 `experiments/ch04/client.py`。

## 服务做了什么

核心只有两层：`experiments/common/engine.py` 是第 02 章循环的逐 token 生成器；`server.py` 把它包进 FastAPI。普通请求把所有 token 拼完再返回 JSON；流式请求每产出一个 token，就立刻以 SSE 格式发出：

```text
data: {"choices":[{"delta":{"content":" Once"},"finish_reason":null}], ...}

data: {"choices":[{"delta":{"content":" upon"},"finish_reason":null}], ...}

data: [DONE]
```

## 实测结果

`verify.py` 启动服务子进程，提示词 `Write a short story about a cat.`，上限 40 个 token：

| | 普通请求 | 流式请求 |
|---|---|---|
| 内容 | 完整文本 | 逐 chunk，拼起来与普通请求**完全相同** |
| 首次看到内容 | 全部完成后 | **0.020 s**（第 1 个 chunk） |
| 全部完成 | 同上 | 0.416 s（第 40 个 chunk） |
| usage | prompt 38 / completion 40 | chunk 数 = 40 |

另有两个检查：服务就绪后 `/health` 返回 ok（本机启动约 5 秒）；`max_tokens: 0` 的非法请求被拒绝，返回 422。

## 流式到底改善了什么

用户在 0.02 秒而不是 0.4 秒后看到第一个字，**体感延迟大幅下降**。但总计算量不变，总耗时也没有减少。流式优化的是感知，不是吞吐。

## 当前服务的限制

模型只有一份，引擎里用一把锁让请求排队，同一时刻只服务一个请求。这在第 09 章会成为主角。服务也没有鉴权、限流和超时，不要直接暴露到公网（第 11 章补稳定性）。

## 小结

服务化就是把"逐 token 生成器"接到网络上。流式不是更快，而是更早。
