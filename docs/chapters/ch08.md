# 第 08 章：Prefix Caching

> **状态：PASS**（RTX 4080 SUPER 实测）。证据：[`ch08-prefix_cache.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch08-prefix_cache.json)。

## 问题

很多请求以同一段很长的开头起手：系统提示、工具说明、知识库片段。每次都重新 Prefill 这段前缀，是纯粹的浪费。第 06 章讲过，Prefill 的结果就是 KV Cache；如果前缀相同，缓存可以直接复用。

## 实验设计

```bash
python -m experiments.ch08.prefix_cache
```

- 24 个请求依次发出，共享约 **1845 token** 的系统提示，各自只有一句不同的短问题。
- 每个请求只生成 1 个 token，所以耗时近似等于 TTFT。
- 对比 vLLM 的 `enable_prefix_caching` 关与开；每种配置先用另一段等长系统提示预热 3 次（不让正式前缀提前进入缓存）。
- 贪心解码，两种配置下 24 个输出必须完全相同。

## 实测结果

| | p50 | 最大 |
|---|---|---|
| 关闭缓存，所有请求 | 93.5 ms | 94.1 ms |
| 开启缓存，第 1 个请求（未命中） | 93.6 ms | |
| 开启缓存，第 2–24 个请求（命中） | **36.9 ms** | 39.1 ms |

- 第一个请求要完整 Prefill，耗时与不开缓存时一样，约 93.6 ms。
- 之后命中缓存，只需处理那句新问题，**p50 从 93.5 ms 降到 36.9 ms（约 2.5 倍）**。
- 24 个输出与不开缓存时完全一致：Prefix Caching 是等价优化。

## 为什么不是快几十倍

命中后剩下的 37 ms 是调度、一次 Decode 和采样的固定开销，前缀越长、模型越大，节省的比例越高。这里模型小、前缀不到 2000 token，是保守的结果。

## 什么时候有用，什么时候没用

- **有用**：系统提示固定、多轮对话（历史就是前缀）、同一份文档反复问答。
- **没用**：每个请求的开头都不同；前缀很短；只用一次。
- **要求**：前缀必须**逐 token 完全一致**，哪怕前面多一个空格，后面全部失效。所以把变化的内容放在提示的**末尾**。
- **代价**：缓存占用显存（和 KV Cache 同一块池子），旧缓存按 LRU 淘汰。

## 小结

Prefix Caching 把"重复的 Prefill"变成一次查表。它不改变输出，只改变 TTFT；收益取决于你的请求里有多少共享前缀。
