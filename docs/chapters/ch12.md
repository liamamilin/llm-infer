# 第 12 章：完整交付

> **状态：PASS**（实测）。证据：[`ch12-report.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch12-report.json)、[`ch12-clean_room.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch12-clean_room.json)。

前面十一章各自能跑，不等于**整体**能交付。“交付”在这里的含义很具体：别人拿到仓库，不依赖你机器上的任何东西，能把关键结果复现出来；并且每个对外说的数字都能追到一个证据文件。这一章做两件事，各用一个脚本验证。

## 交付物清单

| 交付物 | 位置 | 作用 |
|---|---|---|
| 依赖锁定 | `requirements.txt`、`requirements-gpu.txt` | 版本全部固定到精确值 |
| 模型锁定 | `experiments/common/config.py` | 模型 ID + 40 位提交哈希，不跟随 `main` |
| 实验代码 | `experiments/ch00` … `ch12` | 每个实验自带断言，失败就退出非 0 |
| 证据 | `evidence/public/*.json` | 每次实测的原始结果、环境、命令 |
| 评估报告 | [评估报告](/chapters/report) | 从证据自动生成 |
| 服务启动命令 | 第 11 章 | `supervisor` + `server`，带护栏 |
| 测试 | `tests/` | 预检、证据完整性、端到端实验 |

没有容器镜像：本机没有 Docker，没验证过的 Dockerfile 不放进交付物。

## 1. 评估报告：表格里的数字只从证据里来

```bash
.venv/bin/python -m experiments.ch12.report
```

脚本读取 `evidence/public/` 下的全部证据，生成 [评估报告](/chapters/report)（实验清单和关键数字表是程序生成的；“局限”一节是手写的），并检查：

| 检查 | 含义 |
|---|---|
| `all_evidence_pass` | 每个证据文件状态为 PASS，且所有断言为真 |
| `model_revisions_pinned` | 每个证据里的模型版本都是 40 位哈希 |
| `runtime_versions_recorded` | 每个证据都记录了运行时版本（第 10 章只汇总，除外） |
| `vllm_version_pinned_in_requirements` | vLLM 版本由 `requirements-gpu.txt` 锁定 |
| `no_private_paths` | 证据里没有本机或服务器的私人路径 |
| `covers_ch00_to_ch11` | 第 00—11 章都有证据 |
| `report_is_deterministic` | 连续生成两次，内容完全一致 |

这个脚本在编写时就发现了一处真实缺口：第 07—09 章的 vLLM 证据文件只记录了 torch 版本，**没有记录 vllm 版本**。证据是实测时产生的，事后不能改，所以报告里把它写成已知局限，并改为检查 `requirements-gpu.txt` 是否锁定了 vLLM。

## 2. 洁净室复现：别人从零能不能跑

```bash
.venv/bin/python -m experiments.ch12.clean_room
```

脚本做的事：

1. `git clone` 本仓库**已提交的 HEAD** 到临时目录（没提交的改动不会被带进去）；
2. 新建虚拟环境，**只**按 `requirements.txt` 安装；
3. 依次运行第 00 章冒烟、第 04 章 HTTP 验证、第 11 章护栏验证，以及证据完整性测试；
4. 检查装出来的版本与 `requirements.txt` 完全一致，且新产生的三份证据都是 PASS。

实测结果（Apple M4 Pro，Python 3.12.14，克隆的提交 `75b8b11`）：

| 步骤 | 耗时 | 结果 |
|---|---|---|
| 克隆 + 建 venv | 1.2 s | 成功 |
| `pip install -r requirements.txt` | 33.1 s（本机有 pip 缓存；更早一次未走缓存的尝试用了 263.7 s，那次运行因后续步骤失败，证据未收录） | 版本与锁定一致 |
| 第 00 章冒烟（含下载模型） | 192.3 s | PASS |
| 第 04 章 HTTP 验证 | 5.4 s | PASS |
| 第 11 章护栏验证 | 30.3 s | PASS |
| 证据完整性测试 | < 0.1 s | OK |

**这个脚本第一次运行就失败了**，并且抓到一个本机多次运行都没暴露的真 bug：第 11 章服务的日志在多线程下会把两条 JSON 写到同一行（详见[第 11 章](/chapters/ch11)）。这正是洁净室的价值：脚本在干净环境里换了一次时序，缺陷就出现了。修复后重跑，全部 PASS。

## 复现范围：哪些能复现，哪些不能

| | 能否按本书复现 | 说明 |
|---|---|---|
| 第 00—06、11、12 章 | 能（Mac / Linux / CPU 均可，数字因机器而异） | 洁净室验证过第 00、04、11 章 |
| 第 07—09 章 | 需要 NVIDIA GPU 与 `requirements-gpu.txt` | 洁净室**没有**覆盖，没有在第二台机器上复现过 |
| 第 10 章 | 能 | 只读证据，不需要 GPU |
| 具体数字（tok/s、延迟） | **不保证相同** | 取决于硬件；复现的是方法和结论的方向 |

最后一条要说清楚：洁净室验证的是“流程能走通、断言能通过”，不是“数字一样”。性能数字换一台机器就会变，所以本书所有断言都是**关系型**的（“缓存命中更快”“护栏下最坏情况更小”），而不是死等某个绝对值。

## 本书没有做的事

- 没有在第二台 GPU 机器上复现第 07—09 章。
- fp8 质量没评估；SGLang、llama.cpp、TensorRT-LLM 没测试。
- 没有验证多副本、鉴权、TLS 和容器化部署。
- 第 09 章 vLLM 并发 128 档首次出现过 4 个失败请求，之后重测为 0，原因未查明。

想把这些补上，方法在书里都有：照第 09 章的方法压测，照第 12 章的清单检查证据，照洁净室脚本验证复现。
