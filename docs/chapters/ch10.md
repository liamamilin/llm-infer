# 第 10 章：引擎选型

> **状态：PASS**（由第 07—09 章的实测证据汇总得出，无新增 GPU 测量）。证据：[`ch10-decide.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch10-decide.json)。

```bash
python -m experiments.ch10.decide
```

## 比较对象与范围

只比较我们**真正测过**的两个：

- **Transformers**：第 04 章自己写的服务，单线程串行；
- **vLLM 0.32.0**：连续批处理 + Prefix Caching + fp8。

**SGLang、llama.cpp、TensorRT-LLM 等没有测，本书不对它们下结论。** 想评估它们，请照第 09 章的方法在自己的环境里跑同样的压测。

## 汇总数据

同一张 RTX 4080 SUPER、同一个 1.7B 模型：

| | Transformers 服务 | vLLM |
|---|---|---|
| 启动到就绪 | 7.4 s | 34.5 s |
| 启动后占用显存 | 4.1 GB | 16.3 GB（预留 KV 池） |
| 单请求端到端（128 token） | 2.25 s | 0.73 s |
| 并发 1 吞吐 | 56.9 tok/s | 169 tok/s |
| 并发 16 吞吐 | 42.0 tok/s | 2199 tok/s |
| 并发 16 TTFT p50 | 44.8 s | 0.073 s |
| Prefix Caching | 无 | 命中后 TTFT 约快 2.5 倍 |
| 量化 | bitsandbytes：省内存、更慢 | fp8：省内存、吞吐 +23% |

`decide.py` 会校验这些数字互相一致（同一张 GPU、来源证据全部 PASS、结论方向成立），避免正文与证据脱节。

## 决策流程

<Figure name="ch10-decision" caption="按瓶颈选方案。（示意图）" />

1. **只有一个用户、做实验或写原型** → 直接用 Transformers。启动快、可调试、代码就是教材。
2. **有并发，或者在意吞吐成本** → 换 vLLM 这类带连续批处理的引擎。差距在并发 16 时已经是 50 倍量级。
3. **请求共享长前缀** → 开 Prefix Caching（第 08 章）。
4. **显存紧张** → 先考虑量化，但要知道 bitsandbytes 省内存不省时间（第 07 章）。
5. **没有 NVIDIA GPU** → 本章结论不直接适用；Mac / CPU 请回到第 00—06 章的路线，并自行评估 llama.cpp 等。

## 引擎不能替你解决的事

- 质量：换引擎、换精度都可能改变输出，上线前要在**自己的评测集**上验证。
- 稳定性：超时、限流、健康检查、日志是下一章的内容，和引擎无关。
- 成本：吞吐高不等于便宜，要把 GPU 租金、利用率和峰值流量一起算。

## 延伸实验

1. 把自己业务的流量特征（并发、提示词长度、输出长度）填进第 09 章的压测，用同样的表格重做一次选型。
2. 挑一个本书没测的引擎，按第 09 章的方法测一遍，并把结果以 `NOT_RUN`→`PASS` 的方式记入证据。

## 小结

选型就是回答三个问题：有没有并发、有没有共享前缀、显存够不够。每个答案都能用本书的压测脚本在你自己的机器上验证，不要靠别人的榜单。
