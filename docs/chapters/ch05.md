# 第 05 章：基准测试

> **状态：PASS**（实测）。证据：[`ch05-bench.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch05-bench.json)。数字只代表这台机器与这套软件版本。

## 指标定义

| 指标 | 含义 | 主要受什么影响 |
|---|---|---|
| TTFT | 请求发出到第一个 token 产生 | Prefill，prompt 越长越大 |
| TPOT | 之后相邻两个 token 的平均间隔 | Decode |
| tokens/s（decode） | 1 / TPOT | Decode |
| 端到端延迟 | 请求到最后一个 token | TTFT + (N−1) × TPOT |

`bench.py` 里验证了最后一行的恒等式，每次测量都成立。

## 怎样才算公平

1. **固定输入输出长度**：忽略 EOS，每次都精确生成 64 个 token，否则"生成得短"会冒充"跑得快"。
2. **预热**：先跑 3 次丢弃。
3. **重复**：每个配置测 10 次，报告 p50 / p95 与标准差，不是单次。
4. **同步设备**：GPU/MPS 是异步的，每个 token 后做 `synchronize` 再打时间戳。
5. **写下条件**：设备、dtype（float32）、batch=1、并发=1、贪心解码。

```bash
.venv/bin/python -m experiments.ch05.bench
```

## 实测结果（Apple M4 Pro / MPS）

| 输入长度 | TTFT p50 | TPOT p50 | decode tok/s | 端到端 p50 | 端到端 p95 |
|---|---|---|---|---|---|
| 32 | 14.9 ms | 10.0 ms | 100.0 | 0.647 s | 0.658 s |
| 128 | 21.3 ms | 9.9 ms | 100.9 | 0.646 s | 0.659 s |
| 512 | 52.5 ms | 10.7 ms | 93.8 | 0.725 s | 0.735 s |

读法：

- TTFT 随输入变长而增长（32 → 512 token，约 3.5 倍），因为 Prefill 要处理更多 token。
- TPOT 几乎不动，Decode 每步仍然只算 1 个 token；512 时略慢一点，因为要读的缓存更长。
- 端到端时间主要由 64 × TPOT 决定，输出长度对总时间的影响远大于这里的输入长度。

## 冷启动不是稳态

未预热的第一次请求（输入 32）：TTFT = **184.5 ms**，而预热后是 14.9 ms，约 12 倍。如果只测一次，你会得出完全错误的结论。线上服务启动后应做一次预热请求。

## 这些数字不能做什么

- 不能外推到大模型，也不能外推到别的硬件。
- 没有测并发，吞吐是并发 1 的 decode 速度。并发下的吞吐—延迟曲线是第 09 章的内容。
- 没有对 CPU / 其他后端做对比，那需要另行测量。

## 小结

TTFT 看 Prefill，TPOT 看 Decode；预热、重复、固定长度、同步设备，缺一就不可信。
