# 第 06 章：内存与 KV Cache

> **状态：PASS**（实测）。证据：[`ch06-kv_cache.json`](https://github.com/liamamilin/llm-infer/blob/main/evidence/public/ch06-kv_cache.json)。

```bash
.venv/bin/python -m experiments.ch06.kv_cache
```

## 内存由什么构成

1. **权重**：参数数 × 每参数字节数。本模型 134.5M 参数，float32 下实测 **538.1 MB**（设备上分配 539.0 MB）。
2. **KV Cache**：随序列长度线性增长。
3. **激活与临时张量**：包括 Prefill 时的 logits。

## KV Cache 的大小公式

```text
每 token 字节数 = 2（K 和 V）× 层数 × KV 头数 × 头维度 × 每元素字节数
              = 2 × 30 × 3 × 64 × 4 = 46,080 B
```

头维度 = 隐藏维度 576 ÷ 注意力头数 9 = 64。注意用的是 **KV 头数 3**，不是注意力头数 9。这就是第 01 章提到的分组查询注意力，缓存只有完整多头注意力的 1/3。

脚本把公式和真实缓存张量逐字节对比，三个长度**完全吻合**：

| 序列长度 | 公式 | 实测缓存 |
|---|---|---|
| 128 | 5.90 MB | 5.90 MB |
| 512 | 23.59 MB | 23.59 MB |
| 2048 | 94.37 MB | 94.37 MB |

长度翻 4 倍，缓存正好翻 4 倍。

## Prefill 的隐藏开销：logits

<Figure name="ch06-kv" caption="数据来自 ch06-kv_cache.json。" />

同一次 Prefill 里，设备分配的增长比缓存大得多：2048 个 token 增长了 **497.8 MB**，缓存只占 94.4 MB。差额是 logits：Prefill 为每个位置都算一份词表打分，2048 × 49152 × 4 B ≈ 403 MB。缓存加 logits 与实测增长相差不到 5%（已作为断言）。词表大、prompt 长时，这是真实的峰值内存来源，生产引擎只对最后一个位置算 logits 来避免它。

## 缓存值不值

对 512 token 的 prompt 生成 48 个 token（贪心）：

| | 耗时 |
|---|---|
| 开启 KV Cache | 0.29 s |
| 关闭（每步重算全部历史） | 2.34 s（约 **8.0 倍**慢） |

两种方式输出的 token **完全相同**：缓存是等价优化，不是近似。代价是内存，换来的是时间。

## 常见故障

- **`device_alloc_growth` 比理论 KV 大得多**：设备分配器还包含 Prefill 的中间激活和 logits，不只是缓存本身；理论值只对应缓存。

## 延伸实验

1. 在 `kv_cache.py` 里把 `LENGTHS` 加上 4096，对照公式预测缓存大小，再运行验证（注意内存）。
2. 换一个 KV 头数更少的模型，用同一公式预测缓存会缩小多少。

## 小结

KV Cache 用线性增长的内存，换掉每步重复的计算。想估算"能放多长的上下文"，先用公式算缓存，再留出权重和 Prefill 峰值。本章只测了 float32 与单请求，量化与并发会改变这笔账，在后面章节讨论。
