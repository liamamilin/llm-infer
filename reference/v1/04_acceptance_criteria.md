# 04｜自动化验收与质量门禁（Acceptance Criteria）

## 1. 总原则

目标不是强迫自然语言模型每次输出同一段中文，而是确保**每个实验在选定环境的功能与可观测结果符合明确断言**。验收证据必须来自真实执行。

## 2. 状态定义

| 状态 | 含义 | 能否计入必选实验验收通过 |
|---|---|---|
| `NOT_RUN` | 尚未执行 | 否 |
| `PASS` | 在目标环境实际执行且所有强制断言成功 | 是 |
| `FAIL` | 执行了，但断言或命令失败 | 否 |
| `SKIP` | 有充分理由按适用条件跳过 | 否（仅允许可选项） |
| `BLOCKED` | 受权限、网络、缺少设备等外部限制 | 否 |

**必选实验不得通过 SKIP 获得章节 PASS。** 如果原本设计的必选项硬件不可用，要修改实验设计并经用户确认“替代目标”后重新执行，而不是暗改成可选。

## 3. 第 0 章强制验收清单

- [ ] 真实环境探测成功，生成结构化记录，未泄露敏感信息。
- [ ] 选型 ADR 写明引擎/模型选择原因及备选淘汰原因。
- [ ] 依赖锁定文件和模型不可变 revision 已记录。
- [ ] 在所选机器上下载/获取模型文件，加载模型与 Tokenizer 成功。
- [ ] 最小推理生成至少 1 个新 Token，输出结构/数据类型有效，没有运行时异常。
- [ ] `max_new_tokens` 等生成限制确实生效。
- [ ] 重新启动进程后，依据章节说明能再次成功运行（从可复现基线开始）。
- [ ] 自动化验收生成 `PASS/FAIL` JSON 结果，并记录实际运行命令、时间及 Git SHA（若仓库已初始化）。
- [ ] `docs/book/00_environment.md` 的每条必做命令均与仓库脚本一致。

## 4. 第 1 章强制验收清单

- [ ] 列出并解释所选模型的实际文件结构（例：权重、配置、Tokenizer、generation config、chat template），只描述**实际存在**的文件。
- [ ] 模型 ID 与 commit revision 可确认，必要的下载文件有 SHA256/文件大小记录。
- [ ] 能读取并解释真实 `config.json` 中至少模型类型、维度相关字段及其含义（字段因架构不同而异）。
- [ ] 能加载 Tokenizer；对给定示例文本，编码结果为合法 token IDs，解码行为有可复现记录。
- [ ] 明确说明权重文件不等于完整运行程序，计算逻辑由模型架构实现与执行后端共同提供。
- [ ] 区分模型权重容器格式与跨框架交换/执行格式（例如 safetensors/GGUF/ONNX），不声称统一通吃。
- [ ] 完成自动验收，并有模型与文件检查的真实运行证据。
- [ ] 章节文字、示例命令与项目实际模型 revision 一致。

## 5. 后续章节通用门禁

1. 章内 **100% required experiments = PASS**；所有可选实验状态真实披露。
2. 每项关键主张有本机证据，或标注为来自所引用的正式规范/文档；对于依赖版本的行为要标版本。
3. 文档里每条核心命令至少由一个真实验收路径覆盖。
4. 受控输入运行成功，同时至少有一个失败输入/异常处理验证（适用时）。
5. 可重复执行，不依赖 Codex 的临时 shell 状态、未公开的路径或隐式手工改动。
6. 错误报告包含可操作的修复线索，不能隐藏警告/错误。
7. 依赖/模型/启动参数变更需触发相关回归测试。

## 6. 一次真实运行记录的最低数据格式

```json
{
  "run_id": "<generated-at-execution>",
  "chapter": "00",
  "experiment_id": "E00-02",
  "status": "NOT_RUN",
  "started_at": null,
  "duration_seconds": null,
  "command": "<resolved-and-tested-command>",
  "exit_code": null,
  "assertions": [],
  "environment_lock_sha256": null,
  "model_revision": "<commit>",
  "git_sha": null,
  "stdout_path": null,
  "stderr_path": null,
  "failure_reason": null
}
```

这是**模式示例**，并非当前项目已经测试成功的数据。由实际执行器填充，不得在生成教材时手工伪造 `PASS`。

## 7. 回归与干净环境验证

- 最低要求：新进程重新运行，确保不依赖 Python REPL 中隐藏状态。
- 进一步要求：在隔离虚拟环境中按冻结依赖安装并测试；若需要重新下载，记录是否能访问来源及本地缓存状态。
- 若要求完全离线复现，必须另行定义离线资产包、校验与分发许可；不能只凭“缓存里运行过”声称离线可复现。
- 章节更新后至少重跑当前章及其依赖的 smoke/integration tests。

## 8. 性能验收不是固定跑分

性能实验是否通过，首先取决于**能正确执行基准、收集指标并说明采样条件**，而不是达到臆造的 tokens/s 或 TTFT 阈值。若业务场景有明确目标，再定义具体 SLA；未给定 SLA 时记录基线与变化，不虚构通用标准。

在缓存、量化、并发相关对照里，要解释不同配置下可能不改善甚至变差的原因；不得删去不符合预期的样本。

## 9. 最终验收报告

每章末尾自动/半自动生成：

- 已完成必选实验数 / 必选实验总数。
- 所有实验状态、失败原因及证据路径。
- 实测环境、模型/依赖版本、验证时间。
- 章节文档与命令一致性结果。
- 未解决限制、对其他环境的适用边界。

仅当全部必选实验通过且文档审核通过，章状态才可标为 `REVIEWED`。

## 10. 失败处理合同

发现失败时：复现 → 记录 → 缩小问题 → 修复 → 重跑 → 更新文档与日志。无法解决的则报告 `BLOCKED/FAIL`，明确下一步需要用户决策，不应编造运行成功结果或跳到下一章掩盖失败。
