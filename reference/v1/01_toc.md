# 01｜全书目录与实验路线（TOC）

## 共同实践主线

使用一个**小型、已固定版本的开源自回归语言模型**，在同一实际环境中逐步建成可调用的推理服务。每章首先证明实验能跑，再写教材。对不适合设备的技术，提供清楚标注的可选路径，不得伪称通过。

> 章节编号为书中编号，实验编号形如 E03-01。只有 `required=true` 的实验必须在目标环境通过，才能将该章状态设为 PASS。对于确实只能在指定硬件运行的进阶实验，使用“硬件限定/可选”并说明替代学习目标。

## 各阶段的边界

### 基础阶段（00—04）

以“模型实际跑通”为第一性目标。讲清模型文件、Tokenizer、推理执行、生成与 HTTP 服务。这里可选通用兼容运行时，避免一开始引入只支持特定 GPU 的后端。第 00 章的最小生成 smoke test 不意味着第 02 章的知识内容提前完成。

### 测量阶段（05—06）

区分 TTFT（从发起请求到实际收到第一个内容 token 的时间）、端到端延迟、Token 生成速率、吞吐量、内存/显存等；注明计时范围、模型预热状态、服务/客户端是否同机、网络是否计入。KV Cache 的存在和复用是重点，不要求实现注意力算子。

### 优化阶段（07—09）

所有优化实验都必须首先检查**引擎与硬件是否支持**。若主线引擎没有某项功能，可引入第二个受支持的后端作为独立实验，标记为硬件限定；否则只写机制、公开文档与不能实测的原因，不创建假的基准结果。

### 交付阶段（10—12）

基于已经实测的数据讨论部署、资源和成本，不在脱离环境的情况下硬编码性能数字。综合练习要能从 clean start 重建服务。

## 小模型的教学价值及局限

- **可以学习的共性**：模型资产结构、Token 化、模型加载、自回归生成、服务接口、指标采集、配置/日志/压测与大多数诊断方法。
- **不应直接外推的特性**：大模型多机并行、专家并行（MoE）、超长上下文、GPU 饱和条件、网络瓶颈、生产级请求混部、量化后质量表现等。
- **不可做出的结论**：“在 100M/500M 参数上快，所以 70B 也会快”；或者“本地运行正常，所以大型多 GPU 生产环境也能无修改运行”。

## 章节验收顺序

章节状态流转：`DRAFT_PLAN → IMPLEMENTED → EXECUTED → VERIFIED → WRITTEN → REVIEWED`。

禁止仅凭论文、文档或网络文章就将未执行实验标成 `EXECUTED`。更不能先将整本书生成后才让测试追认。

## 写作体量控制

每章建议 1 个主实验 + 1—2 个对照实验 + 1 份最小验收脚本（根据复杂度调整），把案例代码和命令直接写进章节；可同时提供同源仓库文件路径。正文不要依赖读者先下载不透明的 ZIP 才能看懂案例。首次交付重点在准确与闭环，不追求篇幅。
