# 03｜教材生产规范（Production Spec）

## 1. 生产模式

**规格先行 → 代码实验 → 本机运行 → 自动检查 → 人工核对 → 写作 → 一致性复审。**

每章内容必须从有据可查的实验产物回填，而非凭语言模型的想象先写一篇“似乎可以运行”的文章。

## 2. 建议仓库结构

```text
inference-practice-book/
├── README.md
├── AGENTS.md                       # 本项目对 Codex 的常驻协作规则
├── docs/
│   ├── book/                       # 正文章节，编号命名
│   │   ├── 00_environment.md
│   │   └── 01_model_assets.md
│   ├── environment_report.md
│   ├── adr/                        # 选型与重要改动记录
│   └── troubleshooting.md
├── experiments/
│   ├── ch00/
│   └── ch01/
├── scripts/                        # 探测、安装、自动验收、生成验证报告
├── tests/                          # smoke / integration / consistency
├── configs/
│   └── environment.lock.json
├── evidence/
│   ├── environment.json
│   ├── runs/                       # 按日期+章编号隔离日志、结果
│   └── acceptance.json
├── requirements/                   # Python lock / 环境说明，按选定技术生成
└── .gitignore                      # 不提交模型权重和任何秘密
```

目录是推荐约定；可以简化，但不得丢失可执行案例、可复现依赖和验证证据的对应关系。模型权重通常从权威仓库下载或从用户授权缓存加载，不应默认直接提交 Git。

## 3. 一章的必备结构（每章同一模板）

1. **本章的能力目标**：学完能做什么，且可被验证。
2. **知识地图**：必要概念的关系，避免理论铺垫过长。
3. **前置条件**：已完成的章节、具体环境/依赖、所需资源。
4. **实验问题**：要观察什么？假设是什么？
5. **运行方法**：环境准备、完整代码或可读取的短片段、可复制命令。
6. **自动验收**：执行命令、通过断言、失败时输出。
7. **实测结果**：链接到实际 evidence，不复制臆造的日志。
8. **现象与解释**：只能根据真实结果及可靠文档解释。
9. **常见故障**：确实遇到的错误，以及可核查的常见错误。
10. **边界与迁移**：这套方法在大模型、不同设备上哪些部分不再直接成立？
11. **本章小结/练习**：少量能反馈理解程度的问题。

## 4. 实验设计要求

每个实验维护一张“实验卡”：

```yaml
id: E00-02
chapter: 00
purpose: "在选定设备上完成一次最小文本生成"
required: true
prerequisites:
  - "E00-01 PASS"
entry_command: "<actual-tested-command>"
pass_checks:
  - "程序退出码为 0"
  - "新生成 Token 数至少为 1，且不超过配置的上限"
  - "解码成功，无 NaN/非法值/异常"
evidence_path: "evidence/runs/<run-id>/E00-02.json"
status: NOT_RUN
```

允许在代码仓库里以 JSON/YAML/Markdown 存实验卡，字段要可追溯。不得把示例中的占位符提交成最终值。

## 5. 防止教材与代码漂移

- 正文里的命令、文件路径、函数名称，必须与仓库真实内容一致。
- 正文展示的代码，如果经过删节，要注明省略部分和完整文件所在路径；不能让残缺代码看上去能直接运行。
- 建议由测试脚本或自动检查工具检查文档中的必要命令、路径和代码片段。
- 如果为修复实验改了参数或依赖，必须同步修改正文与验收记录。
- 代码与文档共同提交；每章保留修订信息和最后一次验证的 Git SHA。

## 6. 测试层级

- `static`：目录、配置格式、引用文件存在、无秘钥与失效路径。
- `unit`：无模型依赖的分词/格式/结果解析等小逻辑（适用时）。
- `smoke`：最小模型加载与单轮生成/文件检查。
- `integration`：真实模型、真实端点或跨模块流程。
- `benchmark`：独立运行的性能实验，不与正确性混为一谈。
- `docs`：文档命令与实际实现的一致性检查。

至少提供统一入口，例如 `scripts/verify_ch00.sh`、`scripts/verify_ch01.sh` 或等效跨平台 Python 命令；具体路径和方式应在本地验证后定稿。验收产生机器可读 JSON 状态及控制台总结。

## 7. 证据规范

每次运行建议记录：

- `run_id` / 实验 ID / Git SHA / 模型 revision / 依赖锁摘要。
- 实际运行命令及已脱敏参数。
- 退出码、开始结束时间、耗时、执行状态。
- 断言的逐项 PASS/FAIL；模型输出只存非敏感测试文本。
- `stdout` / `stderr` 可单独存档；大文件存路径及 hash。
- 若为性能实验：预热轮数、重复轮数、并发、输入输出 Token 数、原始样本及聚合方法。

不得把示例输出、推测结果、网络教程中的日志当成自家实测 evidence。

## 8. 性能章节的科学性约束

- 先定义 TTFT 起点和终点。HTTP 流式场景里，TTFT 应止于**客户端收到第一个内容 Token**，而不是收到首个空事件、headers 或连接成功。
- 不要混淆 TTFT、TTFB、TPOT、端到端延迟、每秒输出 Token、吞吐量。
- 把 warm start / cold start、预热、缓存命中、输入长度、生成长度、并发、设备负载、tokenizer 的时间是否计入都写清。
- 比较优化方案时尽量只改一个主要变量，并报告质量和稳定性代价。
- 每组取多次样本，报告均值、中位数及波动；不要将一组数据归纳为所有硬件的结论。

## 9. 角色分工（即便只有 Codex 一人）

Codex 分别执行：实现者（写实验）、执行者（运行并保留证据）、审阅者（检查命令/输出/解释对应），通过独立检查表分开记录结论。不能自证“我认为代码正确”就替代真实执行。

## 10. 章节发布门槛

一章可以进入 `REVIEWED`，当且仅当：必选实验在目标环境 `PASS`、测试可再次运行、模型与依赖已锁定、正文可独立操作、证据完整、故障说明真实、用户对有条件跳过项目无歧义。首轮仅允许提交 ch00、ch01；其余章节保持计划状态。
