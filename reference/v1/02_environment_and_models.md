# 02｜环境发现、模型选择与版本冻结

## 1. 核心原则：环境由事实决定，不靠猜

Codex 首先在**用户提供的实际执行环境**只读探测以下信息，并保存原始输出（必要时脱敏）。

| 项 | 需要记录的内容 | 说明 |
|---|---|---|
| OS | 系统、版本、架构 | Linux/macOS/Windows，x86_64/arm64 等 |
| CPU/内存 | 型号、逻辑核数、物理/可用内存 | 不需收集用户姓名或设备序列号 |
| GPU | 厂商、型号、可用显存/统一内存、驱动 | 可能没有 GPU，也可能是 CUDA/MPS/其他 |
| 软件 | Python、编译器、Git、包管理器 | 只读记录，不先安装 |
| 运行能力 | CUDA/MPS/CPU 后端是否实际可用 | “检测到设备”不等于“引擎能运行” |
| 网络 | 能否访问公开模型仓库/包源 | 只做授权范围内的连接性检查 |
| 预算与权限 | 可下载大小、是否可安装依赖、是否允许启动本地服务 | 若缺失，先询问；不能擅自购买云资源 |

不应推断“用户以前拥有某款电脑，所以这次也用它”。环境探测结果保存为 `evidence/environment.json`（机器可读）及简短的 `docs/environment_report.md`；私人路径、账号、令牌不写入仓库。

## 2. 主线模型的筛选条件

优先考虑 **约 0.1B—1B 参数**范围内的小型、公开可下载、自回归文本生成模型；具体大小由机器的实测能力决定。选型清单：

1. 能在目标环境可靠加载并运行，尽量不依赖特定厂商 GPU。
2. 有清楚的模型仓库和合法使用条款；如需登录或同意许可证则先获授权。
3. 提供可检查的权重、模型配置、Tokenizer 和（聊天模型适用时）chat template。
4. 支持被选择的推理库/引擎；若需要特殊代码或 `trust_remote_code`，须说明安全与兼容风险，默认不启用。
5. 固定模型仓库 revision 到不可变 commit hash，记录下载文件 hash、体量与磁盘位置约定。
6. 小模型的**教学目标是跑通流程**，不是要求它具备很强的中文问答能力；不得用回答质量差来证明引擎有问题。

候选示例：`HuggingFaceTB/SmolLM2-135M-Instruct`（仅为候选，不等于已验证适配）；Codex 应先核查仓库可访问性、许可证、模型文件与本机可运行性。若不适合，选相近规模的公开模型并在 ADR 中记录原因。不得把候选的未核实硬件占用、速度或许可证细节写为确定事实。

## 3. 引擎/后端选择（从简到繁）

**第一选择：通用、能跑通的小模型加载路径**，如 `transformers` + 设备适配后端。优先把第 00—04 章的基础流程跑通，再扩展高吞吐量服务。

| 环境情况 | 可尝试的主线 | 附加说明 |
|---|---|---|
| 仅 CPU | Transformers CPU 或兼容的 llama.cpp 模型格式 | 重在正确性，允许较慢；需判断模型格式 |
| macOS / Apple Silicon | Transformers 可用的 MPS 路径，或 llama.cpp Metal | 实测兼容性，关注统一内存与算子支持 |
| NVIDIA GPU | Transformers CUDA，后续可选 vLLM / SGLang | 检查 GPU 支持矩阵、驱动、Torch/CUDA 兼容性 |
| 云端其他 GPU | 根据供应商的受支持框架选型 | 不能假设能运行 CUDA 专属框架 |

这里的后端建议是**备选方案**，不是保证可跑列表。代码路径应只实现目标环境已证实可运行的一个主线，不要为了形式完整而引入所有引擎。

## 4. 版本与可复现性

必须锁定：

- 模型 ID、revision commit hash；按需记录文件 SHA256。
- Python 主/次版本，推理库、深度学习框架、服务库及其版本/锁文件。
- 重要系统依赖（驱动、CUDA/Metal 相关运行时及构建工具）。
- 启动命令、随机数种子、生成参数、设备策略、dtype 及内存限制。
- 实验执行时间（ISO 8601）、机器资源、Git 提交 SHA。

动态变量不必伪装成可冻结：GPU 驱动、操作系统修补、系统负载等无法仅由 Python lockfile 固定，要作为环境前提单独列出。

## 5. 统一记录结构（建议）

`configs/environment.lock.json` 至少包含：

```json
{
  "schema_version": "1.0",
  "target_profile": "local-cpu-or-selected-device",
  "os": "<detected>",
  "architecture": "<detected>",
  "python": "<verified-version>",
  "device": "<verified-backend>",
  "model_id": "<verified-repository>",
  "model_revision": "<immutable-commit-sha>",
  "engine": "<verified-engine-name>",
  "engine_version": "<verified-version>",
  "dependencies_lock": "<path-to-lockfile>",
  "verified_at": "<timestamp-from-real-run>"
}
```

这些占位符只能在真实探测后替换；不得将上述样例当作通过证据。涉及硬件私密信息时只存可复现所需最低限度的信息。

## 6. 在首轮必须验证的最小闭环

1. 环境探测、查看可用空间与网络访问条件。
2. 能够创建隔离环境并安装锁定的依赖。
3. 能够获取模型且记录实际 revision。
4. 可成功加载模型与 Tokenizer（可能涉及加载延迟）。
5. 输入一个非常简短的文本，生成至少一个合法的新 Token，解码得到字符串；记录运行状态与耗时。
6. 第二次**从新进程**使用锁文件复现执行，核验所需文件已完整就绪。

若任一步失败：保留日志、明确失败类别与可选后路；不要继续写“已成功运行”的教材描述。

## 7. 资源计算是估计，不是保证

模型仅权重的理论占用可以粗略估算为 `参数数 × 每参数字节数`，但实际运行还包括缓存、临时张量、运行时、服务进程及内存碎片；真实可用性必须以加载和推理结果为准。量化格式的额外元数据与不同引擎实现可能改变计算结果。

## 8. 多环境支持的策略

首轮只对 **一个实际验证通过的目标 profile** 提供 PASS 承诺。未来如添加 Linux CUDA/macOS Metal/CPU 等 profile，必须各自执行相同主干验收并保留独立记录。未验证的环境仅可写“参考方法/待验证”，不能写成“已支持”。
